The aura Tool

The aura file at the project root is a single-file PHP CLI (1,842 lines, ~49 KB) that drives every development workflow — generation, migrations, seeding, the dev server, key generation, and project introspection. It is standalone, requires no Composer autoloader for most commands, and uses ANSI-coloured output via custom write() / writeln() helpers.

Shebang: #!/usr/bin/env php · Version: 1.2.0 (a global $version variable, separate from the framework's 1.0.0).

Why it's a single file

Every generator, command, and helper lives in one place so the tool:

  • Has zero install step — just chmod +x aura (already done) and run.
  • Doesn't depend on Composer's autoloader being present (it does its own require_once of system/core/{base,database,query-builder,schema}.php when it needs them).
  • Reads project config from the filesystem using three constants: AURA_ROOT, AURA_SYSTEM, AURA_SITE.

Argument Parsing

Lines 160–173 implement a tiny but effective parser:

$args        = array_slice($argv, 1);   // strip script name
$command     = $args[0] ?? 'list';
$commandArgs = array_slice($args, 1);

$options = [];   // assoc: --key=value OR --flag=true
$params  = [];   // positional
foreach ($commandArgs as $arg) {
    if (strpos($arg, '--') === 0) {
        $parts = explode('=', substr($arg, 2), 2);
        $options[$parts[0]] = $parts[1] ?? true;
    } else {
        $params[] = $arg;
    }
}

That's it — no external library, no getopt, no Symfony Console. Every command receives $params (array of positional) and $options (assoc array of flags).

Notable: there is no $command_aliases. Aliases are hard-coded in the dispatch switch (e.g. 'help' / '--help' / '-h' all go to the same case).

Helper Functions

I/O

write($text, $color = null) Echoes $text wrapped in an ANSI color code. Allowed colors: green, red, yellow, blue, cyan, magenta, gray, reset, bold. Always emits \033[0m after the text. writeln($text = '', $color = null) write($text . "\n", $color) success($text) / error($text) / info($text) / warn($text) Shorthand for green / red / cyan / yellow writeln() calls. done() Prints the literal ' DONE' in green — used per-migration and per-seeder progress indicator. confirm($question) Prints $question, reads a line from STDIN, returns true if the trimmed answer is yes or y (case-insensitive). Used by migrate:fresh, migrate:reset, db:wipe.

Naming conversions

studlyCase($name) Replaces - and _ with spaces, ucwords(), strips spaces. 'add_email_to_users' → 'AddEmailToUsers'. 'add-email-to-users' also works. camelCase($name) lcfirst(studlyCase($name)). Defined but not used anywhere in the current source. kebabCase($name) Inserts - between lowercase→uppercase boundary, lowercases, replaces _ with -. 'UserPost' → 'user-post'. 'user_post' → 'user-post'. pluralize($name) Naive English pluralizer used to derive table names: ends in s/x/z OR sh/ch → +es; consonant y → drop + ies; else +s.

Filesystem & DB

ensure_dir($dir) mkdir($dir, 0755, true) if missing. Used by every make: generator before writing. db_bootstrap() require_onces the four core files (base, database, query-builder, schema) and returns a fresh AuraCore\Database instance. Called by every migration / seed / wipe command. migration_class($filename) Strips the YYYY_MM_DD_HHMMSS_ prefix and .php suffix, then produces Migration_<StudlyCase>. Example: 2024_05_30_120000_add_email_to_users.php → Migration_AddEmailToUsers.

The Dispatch Switch

Lines 1700–1840 implement the command dispatcher. It's a single switch($command) with one case per command, calling the matching cmd_* function:

$exitCode = 0;
switch ($command) {
    case 'list':                  cmd_list($commands, $categories);            break;
    case 'help':
    case '--help':
    case '-h':                    cmd_help($params[0] ?? null, $commands); break;
    case 'serve':                 cmd_serve($options);                break;
    case 'make:controller':       $exitCode = cmd_make_controller($params, $options); break;
    // ... 25 more cases ...
    case '--version':
    case '-v':                    writeln("AuraPHP CLI v{\$version}", 'cyan'); break;
    default:                      error("Unknown command: {\$command}"); $exitCode = 1; break;
}
exit($exitCode);

Generators and migration commands assign to $exitCode (1 on failure, 0 on success); the others don't.

The 14 Generators

Every make:* command follows the same template:

  1. Validate $params[0] — print usage and return 1 if missing.
  2. Check for $options['help'] (where supported).
  3. Compute $className = studlyCase($name), $fileName = kebabCase($name) . '.php', $filePath = AURA_SITE . '/<subdir>/...'.
  4. Guard with file_exists() unless --force is passed.
  5. Build the stub with a heredoc.
  6. file_put_contents() and success("... created: site/...").

Smart Migration Name Parsing

make:migration inspects the name and rewrites both up() and down() bodies accordingly. The patterns are tested in this order:

create_<table>_table up() → Schema::create('<table>', function ($table) { $table->increments('id'); $table->timestamps(); });
down() → Schema::drop('<table>');
add_<col>_to_<table>_table up() → Schema::table('<table>', fn($t) => { $t->string('<col>')->nullable(); });
down() → Schema::table('<table>', fn($t) => { $t->dropColumn('<col>'); });
drop_<table>_table up() → Schema::drop('<table>');
down() → empty Schema::create('<table>', ...) with commented columns.
No match Generic commented-out placeholders for both directions.

Examples

php aura make:migration create_users_table
php aura make:migration add_email_to_users_table
php aura make:migration add_status_to_orders_table
php aura make:migration drop_legacy_logs_table
php aura make:migration add_fulltext_index_to_articles_table   # falls through to placeholder

Migration Commands — Internals

Tracking table

Auto-created on the first migrate or migrate:status:

CREATE TABLE IF NOT EXISTS migrations (
    id          INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    migration   VARCHAR(255) NOT NULL,
    batch       INT UNSIGNED NOT NULL,
    executed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
)
Note: The migrations table DDL is hard-coded MySQL. The migrate:fresh and db:wipe commands also use MySQL-only syntax (SET FOREIGN_KEY_CHECKS, SHOW TABLES) — the migration subsystem is MySQL-only.

File scanning

Every migration command uses the same pattern:

$files = glob("{\$dir}/*.php");
sort($files);   // alphabetical — relies on the YYYY_MM_DD_HHMMSS_ prefix being sortable

The filename is then converted to a class name via migration_class($filename).

Batch tracking

  • migrate reads MAX(batch), increments by 1, and inserts every successfully-run migration of this run with the same $newBatch value.
  • migrate:rollback reads MAX(batch), fetches all rows where batch = $lastBatch ORDER BY id DESC (reverse order), calls down() on each, then DELETE FROM migrations WHERE migration = ? AND batch = ?.
  • migrate:reset loops for ($batch = $maxBatch; $batch >= 1; $batch--) to roll back every batch in order.
  • migrate:refresh = cmd_migrate_reset() then cmd_migrate().
No transaction wrapping. Each up() / down() is called directly. A failed up() prints FAILED + the exception message and returns 1, but partial DB changes are not rolled back by the CLI.

The key:generate Command

Generates a 64-character hex secret (32 random bytes) and writes it to .env:

$key = bin2hex(random_bytes(32));   // 64 hex chars

if (file_exists($envPath)) {
    // Replaces existing APP_KEY=… line in place, OR appends a new one.
} else {
    file_put_contents($envPath, "APP_KEY={\$key}\n");
}
Heads up: The Composer PostInstall class uses bin2hex(random_bytes(16)) (32 hex chars) for the initial key, while key:generate uses 64. The two implementations are inconsistent.

The serve Command

Runs PHP's built-in server with the project root as the docroot:

$cmd = sprintf(
    'php -S %s:%d -t %s',
    escapeshellarg($host),    // default 127.0.0.1
    (int)$port,                  // default 8080
    escapeshellarg($docRoot)  // AURA_ROOT (NOT public/)
);
passthru($cmd);

It blocks (passthru() waits for the child). All file requests are served from the project root so your .htaccess + index.php front-controller handles everything.

The route:list Command

It does not parse routes.php as text. It actually executes the file:

require_once AURA_SYSTEM . '/core/router.php';
$_SERVER['REQUEST_URI'] = '/aura-route-list';   // fake request to satisfy router init
$router = require $routesFile;                 // execute system/config/routes.php
$routes = $router->getRoutes();

This means your routes.php file must return the Router instance. The CLI then renders a colour-coded table (GET=green, POST=yellow, PUT=blue, DELETE=red).

Writing Custom Commands

There is no contract or interface for custom commands — the pattern is plain:

  1. Run php aura make:command my:custom (colons allowed in the name).
  2. Open the generated site/commands/my-custom.php: 
    namespace SiteCommands;

class MyCustom
{
    public $name        = 'my-custom';
    public $description = 'Describe the my-custom command';
    public $usage       = 'my-custom [options]';

    public function run($params, $options)
    {
        // use plain echo, or import Aura helpers
    }
}
  3. Add a case to the dispatch switch in aura (around line 1700): 
    case 'my:custom':
    $exitCode = (new \SiteCommands\MyCustom())->run($params, $options);
    break;

The CLI prints this exact case snippet to your terminal after generation, so you can copy-paste it.

Note: There is no service-provider auto-discovery and no commands config file. The single source of truth is the switch in aura. This keeps the tool small but means every custom command requires editing the CLI itself.

The PostInstall Class

Located at system/installer-needs/PostInstall.php (66 lines). It is intended to be wired into Composer's post-install-cmd hook (and prints the same banner regardless of whether it is, since the project doesn't actually register it).

What it does

  1. Computes $root = dirname(__DIR__, 2) — the project root.
  2. Prints a ╔══ AuraPHP Framework — Installed ══╗ banner.
  3. If .env is missing and .env.example exists, copy() it.
  4. If .env exists and contains a bare APP_KEY= line, generates bin2hex(random_bytes(16)) (32 hex chars — half of key:generate) and replaces it.
  5. Prints a "Next Steps" block (serve, open browser, php aura list).
  6. Calls passthru('php aura list') to dump the command list inside the Composer output.

Relationship with the Framework

The CLI is standalone until it needs the framework:

  • Generators, serve, list, help, key:generate, inspire, and about (mostly) require no framework code — they're pure PHP string templating and filesystem operations.
  • Commands that need the framework opt in explicitly via db_bootstrap() (for AuraCore\Database, Schema, Migration, Seeder, QueryBuilder) or by require_once-ing system/core/router.php (for route:list).
  • route:list is the most invasive: it actually executes system/config/routes.php to get a Router instance.
  • The CLI declares no Composer autoloader bootstrap of its own. It relies on whatever autoload is in scope. When invoked directly (php aura …), framework classes are reached only via explicit require_once of the four core files. When invoked through vendor/bin/aura, Composer's psr-4 (AuraCore\ → system/core/) and the bin: ["aura"] entry in composer.json load everything automatically.

Composer shortcuts

With Composer installed, two scripts are exposed:

composer serve          # → php bin/aura serve
composer route:list     # → php bin/aura route:list
